# Web interface

The main window renders the actual local web application through WebView2, with a small WPF native host for window lifetime and Windows file dialogs. The configuration screens use HTML, CSS and JavaScript. There is no web server, external UI framework, CDN, remote font or background telemetry polling.

The visual direction follows DCS's dark graphite surfaces, clear launcher navigation and aviation context, using original amber/blue graphics and an original fighter illustration. The pages separate the features (Quad Views, DLSS 5, Framegen, CPU Boost), file paths, checks and restoration. The frame-rate summary shows what DCS must render, the DCS frame limit and the headset refresh rate, calculated from the settings rather than measured. Pipeline graphics describe the profile; they do not claim live gaze or FPS.

## Controls and motion

Every profile field that changes what is written is represented. Real but rarely changed settings sit in a closed disclosure at the foot of their card (Alternative Quad Views provider, OpenXR runtime override, In-headset diagnostics, Advanced DLSS 5 image controls); search and setting links open it. Profile fields that no longer change anything (the Sboys driver folder and the self-reported limiter and motion-smoothing states) are not shown; old profiles that contain them still load. Numeric inputs retain imported precision, reject incomplete/nonfinite/out-of-range values, and pair with adjustable sliders. Values are raw ratios or multipliers, labeled accordingly. Inactive provider or neural settings remain visible and disabled. Defaults and game quality stay unchanged until the user edits or selects settings.

Ctrl+K opens a searchable settings palette (every field plus the feature checklist, the Pimax Play focus values and the CPU Boost plan); Ctrl+1 through Ctrl+9 open the first nine pages. Search scrolls to and highlights a setting. Keyboard focus is visible. Buttons, labels, switches, dialogs and live status use standard semantic elements. Page transitions last 220 ms; control feedback lasts 100–160 ms. Animations follow Windows' own setting (Settings → Accessibility → Visual effects → Animation effects, seen by the page as `prefers-reduced-motion`); the app has no motion toggle of its own. The only looping animation is the temporary busy marker.

WebView2 is asked to suspend when the window is minimized and resumed when restored. Inventory capture, component verification and deployment run off the UI thread; native commands are serialized. There are no hidden quality reductions in the web migration. UI responsiveness and overhead have not been benchmarked during an actual DCS session.

## Native command bridge

The origin `https://dcs-vr.example/index.html` maps directly to the packaged `ui` folder. External navigation, windows, downloads and browser permissions are disabled. A restrictive content security policy allows only local assets. The host accepts JSON commands from that exact page. The backend owns plan content; JavaScript receives metadata, never DLL payloads. Launch DCS and Apply without launching send the current draft and paths, and the backend builds, validates and checks the plan itself at that moment, so no approval token or earlier preview is involved. Every edit drops the reviewed file list, including an invalid numeric entry.

Browse, import, save and diagnostic export use Windows file dialogs. Sboys preparation verifies the pinned archive and its official configuration tool opens only on an explicit click. Launch DCS runs off the UI thread through the same serialized command channel; a second click while it runs is ignored. The Launch button's tooltip says what it will do (launch the applied profile, or restore it and apply the draft first).

## Verification

`DcsControl.exe --web-smoke <output-prefix>` runs actual WebView2 in a never-shown HWND. It exercises actual DOM controls and the real .NET services against fixture paths, launches (apply + launch contract, never starting DCS) and restores both runtime routes, launch with no changes (nothing written), launch after a change (written over the applied profile + launch check), the Recovery card and Back to stock DCS, Apply without launching, double-click protection, the DCS-running lock, exact values, search (including opening folded settings), the Sboys card following the route, the Overview status and last-flight card (from fixture logs in the real formats), the grouped Checks, the feature rows, the key capture fields (record, refuse, cancel, clear, a DCS default with its note, a conflict between the two keys, an earlier version's label), the saved draft and Undo changes, then captures eight pages and the key capture field recording at 1320×920 and 940×660 at 100%, 1320×920 at 150%, and 1700×1240 at 200%, with `prefers-reduced-motion` emulated. The Checks page is captured after Check this PC. It checks horizontal overflow, header/footer visibility, and that the right panel (feature checklist, profile name, setup buttons) fits without scrolling at 1320×920; below 1000 px height the panel footer is compact and a shadow above it shows when the panel scrolls. The host never starts DCS (Launch DCS stops after the launch contract check and says so) and disables desktop dialogs. After the smoke it changes the fixture's Pimax Play values, checks that Launch DCS updates only the Pimax-derived settings in place (same applied profile, new installed hash recorded) and that a later Back to stock DCS completes without conflicts, and captures the panel in the Ready to fly, Pimax changed and updated states. The legacy `--render-smoke` argument now aliases this WebView2 test.

The installed-release test repeats that verification and separately applies/restores both routes with the real user-supplied signed neural DLL. This proves the new interface is connected to deployment; it does not prove DCS's rendering or headset output. Native file dialogs, visible-window resize/minimize behavior, screen-reader usage and in-game overhead still need interactive validation. The Chromium sandbox needs an unrestricted local process environment; restricted execution caused test navigation to time out and was not accepted as a passing run.

## Feature checklist

The right panel lists the five features, one row each, the optimizations every pilot can use first (Engine Optimizations, CPU Boost), then the VR features (Quad Views, DLSS 5, Frame generation; hidden with Optimizations only): checkbox, name, its state on one line (for example "Bundled · eye tracked · Pimax Quick 33% × 33% · 125% · 20%", "Central 70% · Cinematic", "NVIDIA · Auto 2×/3× · renders 45 FPS", "Above normal · 10 apps moved · prefetch fix"; cut with an ellipsis, the whole text on hover) and a chevron to its page. Foveated Super Resolution (Cheeky SR) has its own card on the DLSS 5 page, shown only in stereo: "Performance: DLSS at full quality only where you look, lighter in the periphery. For stereo without Quad Views." With Quad Views the card is hidden and the option is off (turning Quad Views on turns it off; imported and saved profiles are settled the same way), because there DLSS 5 builds on DCS's own DLSS of the focus views; a Quad Views profile never writes `Enabled=1` to Cheeky, and Quad Views with Foveated Super Resolution alone is simply DLSS off (no Cheeky files).

Dependencies resolve as you check. A short note appears under a row only when it matters:

- Quad Views with DLSS 5 uses the bundled Quad Views and the focus adapter; Pimax native Quad Views cannot host the adapter, so that provider is disabled in the menu while DLSS 5 is on. The row says "Bundled: Pimax native can't host DLSS 5." only when Pimax native was the provider you picked; on the Sboys route it says "Bundled: Pimax native is Pimax-route only."
- DLSS 5 without a runtime file shows "Needs nvngx_dlssnr.dll." with **Select file**, which opens the file dialog, only when the profile names no file and the app has no saved copy. An alternative Quad Views folder with DLSS, Pimax Play values that cannot be read, and CPU Boost asking for administrator rights have one-line notes too.
- The runtime file is selected once. A file picked with Browse (DLSS 5 page or guided setup) or found by Detect my setup is verified exactly like deployment (x64, signature from NVIDIA Corporation, DLSS-NR 310.8) and copied to `%LOCALAPPDATA%\DcsControl\runtimes\nvngx_dlssnr.dll`, with `nvngx_dlssnr.json` next to it (version, SHA-256, size, original path, time saved). Only the latest copy is kept; the same file again changes nothing; an invalid file is refused and nothing is saved. A profile whose runtime path is empty, or names a file that no longer exists, uses the saved copy for checks, Preview, Apply and Launch; profiles keep the empty path. A path typed in the field is used instead. Deployment reads the saved copy, checks its hash against the JSON record and verifies it again.
- Under the Runtime file field the saved copy is shown as "Saved copy · version 310.8.0.0 · from <original path>", with where the copy is kept, **Change…** (pick another file, which replaces the copy) and **Forget**. Forget deletes the copy without confirmation (selecting the file again restores it). When the applied profile was installed from the copy, Forget only stops new drafts from using it and says so inline; the file is deleted when that profile is restored. The copy is app state: uninstalling the application leaves `%LOCALAPPDATA%\DcsControl` (backups, interface settings, the saved copy) in place, as before.
- The Quad Views provider (Bundled / Pimax native) is chosen on the Quad Views page.

Below the rows, **Undo changes** appears while the draft differs from the applied profile and puts the applied profile's settings back.

The profile name and id follow the route and the checked features, for example "Pimax · Quad Views + DLSS 5 + Frame generation + CPU Boost" (`pimax-qv-dlss5-fg-boost`). An imported or applied profile keeps its own name until a feature or setting changes. Import and Save, Detect my setup and Guided setup work on the same model. The reference profiles in `ProfilePresets` remain for the CLI (`presets`, `detect`), the release script and tests; the interface no longer lists them.

## Focus area from Pimax Play

With bundled Quad Views, **Focus area source** is either **From Pimax Play's settings** (default) or **This profile**. The first is the same on the Pimax and the Sboys route (Pimax Play's settings are read even when SteamVR drives the headset), and the feature row says "from Pimax Play's settings". With Pimax Play, the app reads `%APPDATA%\Pimax\AppConfig\global.json` at Launch DCS, Apply without launching and Review files, when the Quad Views page opens and on **Re-read**; it never writes Pimax files. Every number shown is in Pimax Play's own units, and bundled Quad Views renders the same focus Pimax would.

The page shows Pimax Play's Quad View controls exactly as Pimax Play shows them for the selected tab (`piplay_quadviews_fine_type`), with Pimax Play's labels, order and rounding. The rules come from Pimax Play's own interface code (pimaxui `app.asar`, quadviewFov store):

- **Quick**: Center Resolution, Peripheral Resolution, Horizontal FOV, Vertical FOV, Vertical Offset, Transition Mode.
- **Fine**: Center Resolution, Peripheral Resolution, Top → Center, Bottom → Center, L-Eye Left → Center, L-Eye Right → Center, R-Eye Left → Center, R-Eye Right → Center, Transition Mode, then Transition Range and Alpha (or Transition Curve for Linear) when the transition is on.
- Center Resolution = round(100 + gaze × 100) (0.25 → 125%). Peripheral Resolution = round(1 + periphery × 99) (0.1919 → 20%; the slider runs 1–100%, not in steps of 5). Quick FOV = round(stored × 100). Fine "→ Center" = floor(stored × 50) (0.66 → 33%, 0.20 → 10%). Vertical Offset = round(−100 + (stored + 0.5) × 200). Transition Range and Alpha = round(stored × 100). Transition Mode −1 Off, 1 Alpha, otherwise Linear. Missing values show Pimax Play's defaults. Pimax rounds half up.
- The sliders come from the `piplay_*` keys (Pimax Play's own); Center/Peripheral Resolution, offset and transition from `runtime_*`. When the sliders and the `runtime_quadviews_fine_fov_*` values Pimax's runtime uses disagree, the page shows both ("L-Eye Right → Center shows 10% but the runtime uses 16%") and says the runtime's are rendered.

The same "%" means different sizes in the two tabs: Quick Horizontal FOV 33% leaves a focus of 67% of the view; Fine Left → Center 33% and Right → Center 10% leave 57%. The conversion is folded under **How bundled Quad Views reproduces this**: the focus share of the view, the pixel density, the peripheral factor, edge blending and, when DCS's log has the runtime's recommended per-eye resolution (stereo "View [0]: Recommended Width=… Height=…"), the focus size in pixels per eye, rounded to an even count as Pimax's runtime does (Quick 33% → 4088 × 4038, Fine 33/10 · 33/33 → 3478 × 2048 at 5424 × 5356):

- `runtime_quadviews_fine_fov_<eye>_<side>` is the share excluded on that side: focus width = 1 − (left + right) ÷ 2, height = 1 − (up + down) ÷ 2, matching the focus resolutions in Pimax's runtime log.
- Pixel density = 1 + `runtime_quadviews_gaze_resolution_scale` × 0.5 (Center Resolution 125% → 1.125×, Pimax's logged `m_focusPixelDensity`). Periphery = `runtime_quadviews_periphery_resolution_scale` as stored (Peripheral Resolution 20% is 0.1919; Pimax logs 0.198 for it).
- Transition Mode Off sets edge blending to 0; Linear or Alpha keep this profile's edge blending. Sharpening and turbo stay editable.
- Bundled Quad Views centres the focus on the gaze, so an off-centre Pimax focus keeps the same total size centred. Bundled Quad Views renders at most 90% of the view per axis; a larger Pimax focus is stated in Pimax units on the page ("Horizontal FOV is 5% … Horizontal and Vertical FOV 10%", or Fine "Left + Right → Center add up to …").

**This profile** edits the focus in Pimax Play's Quick units, converted exactly like Pimax Quick: Horizontal and Vertical FOV q% (5–90) is a focus of 1 − q of the view; Center Resolution c% (100–200) a pixel density of 1 + (c − 100) ÷ 200; Peripheral Resolution r% (16–100; bundled Quad Views needs at least 0.15) a factor of (r − 1) ÷ 99, stored to 4 decimals as Pimax stores them (33/33/125/20 → 0.67 × 0.67, 1.125, 0.1919). The profile keeps its stored fractions; they are only shown rounded to whole percent and change only when edited. New profiles keep the defaults 0.57 × 0.34, 1.125, 0.19 (Pimax Fine 33/10 · 33/33 converted), shown as Horizontal FOV 43%, Vertical FOV 66%, 125%, 20%. Foveated DLSS without Quad Views keeps its own focus width, height and periphery as fractions of the view.

The backend resolves these values when it builds the plan, so the file list, the report and the written `settings.cfg` match. When Pimax Play's values changed since the profile was applied, the status line says so ("Pimax Play changed: focus will be updated to Quick 33% × 33% · 125% · 20% at launch") and Launch DCS updates the focus area before starting DCS ("Pimax Play changed: focus updated to …"). Checks, readiness and Detect my setup state Pimax Play's values in its own words, e.g. "Pimax Play · Quick: Center Resolution 125%, Peripheral Resolution 20%, Horizontal FOV 33%, Vertical FOV 33%, Vertical Offset 0, Transition Mode Alpha." The overview and checklist summaries read "Pimax Quick 33% × 33% · 125% · 20%" or "Pimax Fine 33/10 · 33/33 · 125% · 20%" (L-eye left/right · top/bottom), and "profile 43% × 66% · 125% · 20%" for a profile's own values. With Pimax native Quad Views the page shows the same Pimax Play controls read-only, since Pimax applies them itself.

## CPU Boost page

The page binds the Boost profile fields: DCS priority (Normal, Above normal, High, with the note that High can starve audio and input), moving VR runtime and headset services, moving background apps (editable list, one process name per line), the prefetch fix (Off, Observe, Skip repeats, with the measured effect and its single-player-only testing) and administrator rights. **What Boost will do** is a read-only table from the backend (`boostPlan`, `BoostPlanner.Describe` with `Saved Games\DCS\Logs\dcs.log`): the core ranking source, the cores for DCS, the VR runtime and background apps, each process with its change, whether it runs and whether it needs administrator rights, and notes. Validation refuses empty app names and processes that start DCS (Steam, Explorer, Epic Games Launcher, the DCS launcher and updater, this app) or DCS itself in the move and close lists.

A second card, **Flight helpers**, holds three options that work with or without CPU Boost, all off by default: **Free VRAM before flight** (Programs to close, one process name per line; Reopen after the flight; End programs that do not close), **Small DCS window in VR** (1280×720 windowed in `options.lua`, restored with the profile) and **Lower the monitor while flying** (Monitor mode in flight, a list filled with the modes the primary monitor reports, plus the profile's own mode marked "not reported by this monitor" when it is missing). What Boost will do has one section per option: CPU Boost as before; Free VRAM with each listed program, its running processes and their VRAM (approx.) and the total to free; the `options.lua` values of the small window; and the monitor with its name and current → flight mode. A section whose option is off says so and shows what it would do. The old "apps to close at launch" list is gone; a profile that used it opens with Free VRAM on (when CPU Boost was on), the same names, End programs that do not close on and Reopen off, which is what it did.
## One-click launch

**Launch DCS** is the only primary action. On click it brings the installed configuration in line with the draft shown, then starts DCS:

- **Nothing changed** (the draft has the applied profile.json's content, id and name aside, for the same DCS.exe and options.lua, and every installed file and dependency still matches): DCS starts with the applied files. Nothing is written.
- **Only Pimax Play's Quad View values changed** (profile focus source Pimax Play): only the bundled Quad Views `settings.cfg` and `pimax-fovea.json` of the applied profile are rewritten, through `OriginalsStore.UpdateInstalled`: the files are overwritten and their new hashes recorded for the applied profile; the originals stay as they are. The status line reads "Pimax Play changed: focus updated to Quick 33% × 33% · 125% · 20%". If anything does not match (a file was edited, the profile was applied by an older version without `pimax-fovea.json`, Cheeky's INI also depends on the values, or the bundled settings changed), Launch writes the whole profile again.
- **Only the profile's own DCS settings in options.lua changed** (DCS writes options.lua back, for example a Max FPS set in its own settings): those keys alone are set back to the profile's values in place (`OriginalsStore.RealignLuaValues`); every other key and DCS's formatting stay, and Back to stock DCS still sets the owned keys back one by one, keeping DCS's other changes. The status line names the keys that were set back.
- **The draft differs, no profile is applied, or an installed file or external dependency changed**: the draft is checked like Review files (validation, component hashes) before anything is touched, then written over whatever is installed (`OriginalsStore.Apply`): no restore step and no conflicts. The first time a path is written its original is backed up (or recorded as absent) before anything is written; files an earlier profile wrote that this one does not use go back to their originals; owned options.lua settings the new profile no longer needs go back to the user's values. Another program's file is backed up and replaced, and the status line says so ("Replaced another dxgi.dll (…); it is backed up and Back to stock DCS brings it back."). Then the launch contract is checked.

Any error stops before DCS starts and is shown in the status line; every original stays recorded, so launching again or Back to stock DCS finishes an interrupted apply. DCS must be closed (checked path-aware against the DCS install, Saved Games and the managed folder). The CPU Boost helper still starts with DCS. `DcsVr.Cli launch` runs the same Core code (`ControlService.SyncAndLaunch`) for the applied profile.

The status line shows one state: **Ready to fly** (green dot; the draft is applied to the same DCS.exe and options.lua: a different DCS install or options.lua is a change, and Undo changes brings back the applied ones; an empty path, detected automatically, matches), **Changes will be applied when you launch**, **DCS is running** (Launch, Apply without launching and Back to stock DCS are disabled; the page checks for a running DCS every 4 seconds), **Check numeric values** or **Needs attention** with the error. The secondary links are **Review files** (the read-only list of what Launch writes for this draft), **Apply without launching** (the same steps without starting DCS; Steam or desktop shortcuts still do not pass the profile's OpenXR environment) and **Back to stock DCS** (opens Recovery, shown while DCS Control has changed any file).

**Stock DCS** (the page formerly called Recovery) is one card: "Original files · N files changed by DCS Control", one **Back to stock DCS** button, the last action and its time, a folded list of every path with what Back to stock DCS will do (restore the backup, remove, or set back DCS Control's own options.lua settings) and an advanced **Backups folder** link. There are no per-profile journals or conflicts to resolve.

## Overview and last flight

The Overview opens with one status line: **Ready to fly**, **Changes apply at launch**, **DCS is running** or **Check numeric values**, what Launch DCS will do, the profile name and the applied profile, a count of what to fix or check yourself (a link to Checks, or "Nothing to fix") and, when the draft differs from the applied profile, **Undo changes**. The four feature tiles follow, then **Last flight**.

Last flight is read after DCS exits from the logs the session left (`LastFlight` in Core, `lastFlight` in the bridge; answered outside the command lock and cached by file size and time, so a 40 MB OFXR log is read once):

- The session: `Saved Games\DCS\Logs\dcs.log` ("=== Log opened UTC …", the last timestamped line, "=== Log closed."). Its date, start time and duration are the card title; a log without "Log closed" says DCS did not close normally.
- **Headset**: Pimax's `%LOCALAPPDATA%\Pimax\runtime\pvr_srv_log_*.txt`, the once-a-second "rendering fps:(a:…,c:…) Missed:(a:…) … Discard:(a:…)" lines of the DCS process within the session, loading seconds (under 1 FPS) left out: average FPS delivered, the share of seconds at the refresh rate, missed and discarded frames.
- **Framegen**: OFXR's flight log of the session (`managed\profiles\*\ofxr\ofxr-bridge-flight-<start>-pid<n>.log`): the share of seconds at 2× and 3× (`latency_status`), whether adaptive control ran and how often it switched (`adaptive_switch`).
- **DCS frame time**: the median and 90th percentile of the per-second p90 that adaptive control judges, max(CPU, GPU) per DCS frame (`latency_status` a); only with Auto 2×/3×.
- **DLSS 5**: Cheeky's logs in `bin\CheekyFoveatedDLSS` (runtime initialized and its version, failures, hotkey toggles). Every session appends to these logs with the time of day only, so only the lines after the last startup marker count ("Cheeky … initializing; runtime remains resident" in the runtime log, "Initializing standalone host" in the host log).
- **CPU Boost**: `%LOCALAPPDATA%\DcsControl\boost\status.json` (state, apps moved and restored, processes that need administrator rights).
- **Prefetch fix**: `bin\DcsVrPrefetchFix.log`, the 10 s reports within the session (calls per second, share skipped weighted by calls).

A part without its log is left out; without dcs.log the card says "No flight recorded yet", and while DCS runs it says the summary appears after it exits. Numbers that do not parse are skipped, and any unexpected error while reading the logs is written to `%LOCALAPPDATA%\DcsControl\app.log` and shown as no flight, never as a crash. VRAM use is not in any of these logs, so the card does not show it; the in-headset VRAM counter shows it live.

## Checks

Checks lists each finding once, in three groups: **Must fix** (errors that stop Launch DCS), **Check yourself** (warnings and the headset checks only you can do) and **OK** (folded). Each finding is one line, title and text, with a link to the fix (the setting, its page, Recovery or an official guide); a click shows the whole text. Profile checks follow every edit; **Check this PC** adds the runtime, C++ runtime, drivers, write access, route and headset checks. **Export report**, the files Launch DCS will write and, folded, what was detected on this PC follow. The Overview only counts the findings, so nothing is listed twice.

## In-flight keys

The DLSS 5 toggle and the diagnostic panel key are recorded from the keyboard: click the field, press the combination (it shows as "Ctrl+Shift+F12"); Esc cancels, Backspace clears it (Off). A key needs Ctrl, Alt or Shift unless it is an F-key, Pause, Scroll Lock, Insert, Home, End, Page Up or Page Down; Ctrl, Alt, Shift or Windows alone, any combination with the Windows key, keys without a usable key code (IME and media keys: key code 0, 229 or 255 and above) and Windows' own combinations (Alt+F4, Alt+Tab, Ctrl+Esc …) are refused with a short reason, and so is the combination the other key already uses. A combination DCS binds by default (DCS 2.9.30's own keyboard layers, read from `Config\Input`; aircraft modules add their own) is accepted with a note, and Checks lists it under Check yourself. DCS binds physical keys named after the US layout, so the list is converted to the keyboard layout in use through scan codes (`NeuralHotkeys.DcsDefaultsForCurrentLayout`, MapVirtualKeyEx): on AZERTY the warning for DCS's Ctrl+Z appears on Ctrl+W. F-keys, navigation keys and the numeric keypad are the same in every layout. The profile stores the key as "virtual-key:modifiers" (Ctrl 1, Alt 2, Shift 4), the format Cheeky (`DCSVR_NR_HOTKEY`) and OFXR (`DCSVR_DIAG_HOTKEY`) read; profiles of earlier versions hold one of the old menu's labels, which still work and are kept until a different key is recorded.

## Draft kept across restarts

The draft on screen is saved to `%LOCALAPPDATA%\DcsControl\draft.json` 0.7 s after it last changed, with the selected DCS paths. At start the app shows it in preference to the applied profile when the two differ, and says so; **Undo changes** (right panel and Overview) goes back. Save and Import stay for named profile files.

## DCS launcher

**Show the DCS launcher** (DCS & headset) keeps DCS's own launcher window. When Play is pressed, the launcher starts `DCS.exe --restarted` asking Windows to take it out of any job object, and the new process inherits the profile environment. Inside a Windows job that forbids that (DCS Control started by another program that runs its children in a job, such as a script runner or a sandbox) Windows refuses with access denied: dcs.log ends with "Launching process … failed with error code 5" and the game never opens. The app detects this (`LaunchSafety.CurrentJob`): the option is then disabled while off and explained; with it on, Launch DCS stops before writing anything and Checks lists it under Must fix. When the app is in a job whose limits cannot be read, the answer is "unknown": nothing is blocked, the option says so and Checks lists a warning. Opened from the Start menu or Explorer, the app is not in such a job and the launcher works.
